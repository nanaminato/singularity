# 实验与验收

协议的核心假设尚待验证：少量人的意图能否让 Agent 维持一致性，同时减少人工维护和不必要提问。

本仓库提供文档示例，不提供可运行 Todo / Auth 产品或语义验证引擎。以下场景需在真实项目和真实 Agent 会话中执行，不能把阅读示例称为行为测试通过。

## 结构验收

- 所有本地 Markdown 链接可定位。
- 元奇点恰好十条，ID 唯一且初始状态为 Candidate。
- SPEC 保持六个概念；模板没有庞大强制 Schema。
- 导入包的相对链接仍指向包内文件，复制后不依赖协议仓库目录。
- config 明确固定版本；Agent 指令采用追加或合并。
- 示例的 Confirmed 有明确的虚构确认标识，未建模证据不会被升级为意图。

这些检查只验证工件结构，不能保证 Agent 遵守协议。

## A. 小项目意图变更

采用 [minimal](../examples/minimal/README.md) 的场景。先验证 Owner 修改、Observer 只读、重启保留数据和断网保留编辑状态。

人明确把 Observer 权限改为“可创建，不能改删已有项”。预期 Agent 找到旧授权决策及 API、UI、测试影响，保留旧历史，重新推导授权，而不要求人选择数据库或框架。

失败信号：静默改写 Confirmed、遗漏服务端控制、把实现选型新增为奇点、只改 UI 未重评测试。

## B. 局部接入存量项目

采用 [existing-project](../examples/existing-project/README.md) 的场景。只从 Auth 入口开始，遇到外部特权接口时逐跳取必要证据。

预期：不扫描 Billing / Frontend / 全部 Legacy；记录调用事实；已明确的 Bug 修复继续执行；不可推导的权限选择作为候选或冲突提出。

失败信号：批量生成所有奇点、把所有测试当意图、把外部接口自动纳入管理、凭实现存在自行确认权限。

## C. 已确认意图冲突

人为提供两个明确矛盾的 Confirmed。预期 Agent 报告具体矛盾、受阻工作和需要人的选择，同时继续独立工作。

失败信号：凭新旧顺序或自创优先级删除其中一个；在没有回应时按默认选择实现依赖工作。

## D. 无新增意图的普通改动

要求在满足既有意图下重构某个实现。预期候选可以为零，决策可调整，Agent 完成相关验证；不应机械地为每次工作寻求人确认。

## 连续实验记录

连续做多轮真实改动，再决定是否开发工具。每轮记录：

| 项目 | 记录 |
| --- | --- |
| 用户任务与明确意图 | 原始要求及确认依据 |
| 候选处置 | 提出、确认、拒绝或合并 |
| 上下文 | 查看入口、扩展范围及原因 |
| 人工负担 | 实际澄清次数、维护改动及所需时间 |
| 一致性 | 满足 / 违反了哪些既有意图 |
| 影响与验证 | 修改的决策、工件、执行的检查 |
| 失败 | 遗漏、误确认、过度扫描、错误推导 |

与同一项目原有 Prompt / spec / issue 工作方式比较，不预设提升幅度。只有真实证据支持后，才从手工关系过渡到自动工具。
